# Flowmusic Genesis V2: ideas backlog

Этот список относится только к **Omega-Protocol Parameter Synthesizer**: semantic retrieval, Semantic Value Anchoring, Transition Mode, Macro Output и набору параметров Flowmusic.

## Принцип развития

Система уже разделяет задачу на два независимых этапа:

1. Retrieval выбирает релевантные параметры из `unified_parameters_enriched.json` по embedding запроса.
2. Anchoring определяет их значения через прямые числа (L0), лексику направления (L1) и семантические оси (L2).

Новые возможности стоит добавлять так, чтобы для каждого изменения можно было проверить: какие параметры выбраны, почему изменилось каждое значение и стало ли это лучше на фиксированном наборе запросов.

## Приоритет P0: доверие и наблюдаемость

### 1. Панель объяснения результата

Добавить сворачиваемый блок `Why these parameters?` для каждого запуска. В нём показывать:

- исходный и эффективный запрос;
- top-K similarity и домен каждого выбранного параметра;
- источник значения: `numeric`, `lexical`, `axis`, `neutral` или `default`;
- сработавший термин, направление, степень и ось;
- значение до/после и факт clamp/snap.

Польза: можно сразу отличить слабый retrieval от ошибки anchoring и быстро исправлять данные, а не гадать по итоговой ручке.

### 2. Набор пользовательских оценок

После поиска дать две быстрые оценки: `релевантно / нерелевантно` для параметра и `значение верное / неверное` для предложенного значения. Сохранять query, выбранные параметры, финальные ручные правки и оценку в отдельный локальный JSONL-файл.

Польза: реальные сессии станут самым ценным eval-набором. Не требуется LLM в runtime.

### 3. Регрессионная проверка перед публикацией базы

Расширить `eval/eval_set.json` примерами из реальной работы и запускать `eval_anchoring.py --full` перед обновлением dataset, lexical-словарей, осей или модели embedding. Зафиксировать минимальные пороги:

- neutral false-movement rate не растёт;
- directional accuracy не падает;
- для ключевых запросов ожидаемые параметры остаются в top-50;
- значения не выходят за диапазоны и не меняют несвязанные toggles.

Польза: пополнение базы не будет незаметно ломать уже удачные запросы.

## Приоритет P1: удобство синтезаторной консоли

### 4. Режимы плотности без потери данных

Оставить текущий `Console` как рабочий режим на 50 модулей и добавить переключатель `Compact / Inspect`:

- `Compact`: все 50 ручек, короткое имя, значение, цвет домена;
- `Inspect`: выбранный модуль раскрывает русское описание, semantic keywords, диапазон, источник и reason;
- поиск по technical name, русскому описанию, unit и ключевым словам;
- закрепление (`pin`) важных параметров над сеткой.

Польза: один экран остаётся плотным, но смысл сложных параметров доступен без перегрузки карточек.

### 5. Управляемые пресеты и A/B-состояния

Добавить сохранение локальных `Parameter Snapshot`: название, query, 50 значений, включённые instructions и версия index/anchors. Для Transition Mode хранить Snapshot A, Snapshot B и их дельту.

Польза: можно воспроизводить удачные состояния и сравнивать правки без потери контекста.

### 6. Улучшенный Transition Flow

Текущий текстовый flow развить в компактный отчёт с фильтрами:

- `changed only`, `numeric`, `discrete`, `by domain`;
- дельта в абсолютной величине и процентах диапазона;
- монотонный сдвиг `->`, рост `+`, снижение `-`, дискретное переключение `<->`, смешение `<+>`;
- предупреждение для параметров, которые резко меняются около 50%.

Польза: переход становится редактируемой композицией, а не только визуальным эффектом.

### 7. Управление результатом retrieval

Добавить в UI `Top K` (30/50 уже есть) и фильтры по domain/category. При необходимости показывать "ещё N кандидатов" без повторного embedding запроса.

Польза: пользователь контролирует ширину синтеза и не получает шум от соседних доменов.

## Приоритет P1: качество semantic retrieval

### 8. Domain-first retrieval

Перед глобальным top-K определять 1-3 вероятных домена, затем делать diversified retrieval: например, 70% кандидатов из сильных доменов и 30% из соседних. Не исключать глобальный поиск полностью.

Польза: запросы про ритм не будут заполняться десятками случайных timbre-параметров, при этом междоменные запросы сохранятся.

### 9. Дедупликация и разнообразие выдачи

Использовать `dedupe` из enriched dataset и добавить MMR-подобное разнообразие в top-K: не выдавать много почти одинаковых параметров одной подкатегории, если есть релевантные альтернативы.

Польза: 50 контролов становятся содержательно разными и полезнее для macro output.

### 10. Профили запросов

Выделять из query структурированные intent-сигналы: tempo, intensity, space, rhythm, tone, arrangement, voice, production. Это не замена embeddings, а прозрачный re-ranking signal, который отображается в панели объяснения.

Польза: короткие художественные запросы и длинные JSON/Markdown instructions становятся стабильнее.

## Приоритет P1: качество anchoring

### 11. Редактор лексических правил с тестом

Сделать служебный экран для `direction_lexicon.json`, `degree_scale.json`, `markers.json` и `numeric_units.json`: редактирование, preview токенизации, 10-20 тестовых фраз и показ затронутых quantity kinds. Изменения сохранять как версионированный patch, а не перезаписывать основной файл без истории.

Польза: расширение русского и английского словаря становится безопасной операцией.

### 12. Явные правила для Toggle и Select

Для Toggle хранить ясные `on_aliases` / `off_aliases`; для Select - canonical options, aliases и, если порядок имеет смысл, `option_positions`. Не выводить toggle из оси, если не найдено сильного лексического или семантического основания.

Польза: исключает массовые отключения и случайные переключения дискретных параметров.

### 13. Уровни уверенности и подтверждение рискованных изменений

Рассчитывать confidence на уровне результата. Для низкой уверенности показывать proposed value, но не применять его автоматически; для Toggle/Select требовать явного `Apply discrete changes`.

Польза: пользователю проще доверять автоматике, а опасные изменения не происходят молча.

## Приоритет P2: наполнение базы параметров

### 14. Контракт записи параметра

Каждый новый параметр должен иметь минимум:

- уникальный стабильный `technical_name` в `snake_case`;
- `ui_element`, корректный default и допустимый диапазон либо options;
- короткое русское и английское назначение в `semantic_keywords`;
- `category`, `sub_category`, `domain`, `quantity_kind`;
- 1-2 подходящие `axes` и проверенную полярность;
- unit/step для Range, aliases для Select/Toggle;
- 2-5 примерных query, где параметр должен и не должен появляться.

Нельзя добавлять параметр только по красивому имени: без семантики, диапазона и тестов он ухудшает retrieval.

### 15. Пакеты расширения вместо одиночных записей

Добавлять данные вертикальными наборами по 20-80 параметров: например `acid bass`, `microtonal ornament`, `vocal tract`, `spatial FX`. Для пакета включать параметры, aliases, оси/полярность, 10-30 eval-запросов и changelog.

Польза: проще оценивать качество конкретной области и откатывать неудачное расширение.

### 16. Очередь кандидатных параметров

Вести `parameter_candidates.jsonl` отдельно от production dataset. Каждая запись получает статус `draft`, `reviewed`, `accepted` или `rejected`, автора, источник, примеры и причину решения. Только `accepted` попадают в `unified_parameters_enriched.json` и затем требуют rebuild retrieval index/anchors при необходимости.

Польза: база остаётся чистой при совместной работе с несколькими LLM и людьми.

### 17. Нормализация единиц и диапазонов

Создать таблицу конвенций: BPM, Hz, ms, dB, cents, ratio, normalized 0..1, percent 0..100. Для каждого `quantity_kind` определить предпочитаемую единицу и допустимые границы.

Польза: numeric parser и Transition Mode смогут сравнивать параметры предсказуемо.

## Порядок внедрения

1. P0.1 и P0.2: объяснение результата плюс пользовательская обратная связь.
2. P0.3: базовый regression gate и реальные eval-примеры.
3. P1.4-P1.6: плотная консоль, snapshots и читаемый transition report.
4. P1.8-P1.13: domain/diversity retrieval, правила дискретных контролов и confidence.
5. P2.14-P2.17: формализованное масштабирование базы через пакеты и review queue.

## Что не стоит делать сейчас

- Не добавлять LLM-вызов на каждый ввод символа: embedding и поиск должны запускаться явно кнопкой.
- Не встраивать сырой JSON instruction целиком в retrieval без краткого semantic summary.
- Не смешивать Flowmusic V2 с устаревшими генераторами и Semantic Plane.
- Не менять одновременно dataset, lexical rules, axes и embedding model: иначе невозможно понять источник улучшения или регрессии.
