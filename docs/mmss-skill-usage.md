# Справочник использования скилла MMSS Principle Synthesis

Источник: установленный локальный файл `C:/Users/abstract/.codex/skills/mmss-principle-synthesis/SKILL.md`, версия скилла `0.1.3`. Этот документ пересказывает его области применения, а не расширяет их.

## Поддерживаемые операции

- **synthesize** — создать MMSS из источников, требований, существующего стека или смешанного основания.
- **audit** — проверить существующий MMSS/стек и сформировать выводы.
- **validate** — выполнить подходящие структурные, архитектурные, семантические и/или поведенческие проверки.
- **repair** — исправить обнаруженные дефекты в заданном артефакте в пределах разрешённого объёма.
- **extend** — добавить совместимое продолжение существующего MMSS.
- **transfer** — сопоставить механизм с другой областью, отдельно отмечая сохранённые связи, изменившиеся предположения и потерянные/неустановленные гарантии.

Выбирается одна главная операция; вспомогательные проверки не должны подменять цель запроса.

## Виды артефактов

- **module** — компонент с одной основной ответственностью и контрактами.
- **substack** — связанные компоненты с внешним контрактом интеграции.
- **system** — полная архитектура с точками входа и границами интеграции.
- **patch** — предложенное или применённое изменение к указанной базе; предложение нельзя выдавать за применённое изменение.
- **report** — результаты изучения, не требующие архитектурного изменения.

MMSS-json — семейство структурированных документов, а не одна обязательная схема. Для JSON по умолчанию скилл рекомендует envelope `SYNTHESIZED_MMSS_SYSTEM`; явные требования пользователя к файлу/формату имеют приоритет. Внутренние локаторы, источники, состояния проверок, неизвестные значения и ограничения следует сохранять явно.

## Основания и режимы работы

Основание выбирается отдельно от операции:

- **sources** — изучаемый контент формирует основание; содержательные утверждения связываются с фактическими источниками.
- **requirements** — основанием служат требования пользователя; они не подменяются вымышленными исследованиями.
- **existing_stack** — изучаются реальные интерфейсы, пути выполнения, зависимости, побочные эффекты, настройки и тесты имеющейся системы.
- **mixed** — используются несколько оснований с сохранением различий между ними.

Режимы:

- **one_shot** — разовое выполнение; режим по умолчанию.
- **сессия** — работа в рамках сохраняющейся сессии, только если её явно запросили.
- **scheduled** — периодическая работа, только при наличии настоящего поддерживаемого планировщик и разрешённой настройки. Описание расписания само по себе не создаёт запуск или фонового агента.

Пять названий логических ролей для новой полной MMSS: `SYS4_META_GENESIS`, `SYS3_PATTERN_EXTRACTION`, `SYS2_SEMANTIC_WEAVING`, `SYS1_LINGUISTIC_GENERATION`, `LANGUAGE_FIELD`. Это архитектурные роли, а не обязательные отдельные агенты. В существующем стеке компоненты отображаются на роли только там, где есть фактическая ответственность; пустые роли не заполняются фиктивными модулями.

## Примеры запросов на естественном языке

Это примеры формулировок для вызова скилла. Они **не являются зарегистрированными командами IDE или slash-командами**.

- «Создай MMSS-json из существующей реализации этого репозитория, сохрани ссылки на код и отдельно обозначь выводы из структуры.»
- «Проведи аудит этого MMSS: найди неразрешённые ссылки, отсутствующих поставщиков обязательных входов и неявные циклы обратной связи.»
- «Проверь JSON и внутренние контракты документа; поведенческие проверки отметь как незапущенные.»
- «Исправь только невалидные внутренние ссылки в указанном MMSS, сохранив публичные идентификаторы и текущую семантику.»
- «Расширь существующий модуль совместимым интерфейсом и покажи, какие версии/контракты меняются.»
- «Сопоставь механизм извлечения принципов с целевой областью как частичное структурное соответствие; не заявляй изоморфизм без доказательств.»
- «Синтезируй модуль из этих требований, не подбирая внешние источники.»
- «Создай периодическое обновление MMSS только если доступен реальный планировщик; без него подготовь обычный однократный артефакт.»

Если нужны настоящие команды IDE, их регистрацию следует подтвердить в конфигурации/реестре соответствующего приложения. В просмотренном установленном `SKILL.md` описаны операции и правила скилла, но регистрация slash-команд или команд IDE не обнаружена и не утверждается.

## Общие правила использования

- Сначала изучать доступные источники и инструкции проекта.
- Различать наблюдение в коде/источнике, документированное утверждение, вывод из структуры и предложение.
- Для модулей описывать реальные input/output, preconditions/postconditions, зависимости, состояние и его владельца, ошибки и fallback; каждому обязательному входу указывать поставщика.
- Разносить data flow, dependency, composition и feedback; циклы описывать с состоянием, ограничением и условием остановки.
- Не выдавать план проверки за выполненную проверку; parse не подтверждает выполнение, а спецификация не исполняется сама.
- Не вводить мета-формулу, роль, metric, invariant, skill tree или механизм только ради полноты шаблона.
- Не придумывать отсутствующие значения, версии, результаты измерений, происхождение, расписания или поведение.
- Язык человекочитаемых значений выбирать по текущей инструкции пользователя; стабильные ключи JSON и идентификаторы оставлять машинно-стабильными.
