# MMSS Meta Crystal: Руководство по режимам приложения

## Обзор

MMSS Meta Crystal реализует пять различных систем генерации и поиска параметров, каждая предназначена для конкретных задач управления аудио-параметрами. Это руководство объясняет архитектуру, принципы работы, методы и цели каждого режима.

---

## 1. Flowmusic Genesis V3

### Назначение

Flowmusic Genesis V3 — это построитель составного индекса, который создаёт унифицированный векторный поисковый индекс из нескольких источников параметров. Он обеспечивает эффективный семантический поиск по всему каталогу параметров, объединяя эмбеддинги из автономной библиотеки и замороженных комбинаторных наборов данных.

### Архитектура

```
Flowmusic Genesis V3: Пайплайн построения индекса
├── Точка входа скрипта
│   └── main() выполнение
│       └── build() вызов
│           ├── Загрузка источников данных
│           │   ├── Чтение параметров библиотеки
│           │   └── Чтение замороженного набора данных
│           ├── Управление векторным кэшем
│           │   └── Загрузка кэшированных векторов
│           ├── Генерация эмбеддингов
│           │   └── Пакетное эмбеддинг-преобразование через Ollama
│           └── Сохранение индекса
│               ├── Запись бинарных векторов
│               └── Запись манифеста JSON
```

### Принципы работы

1. **Интеграция данных**: Объединяет параметры из двух источников:
   - **Библиотека**: Автономная библиотека параметров V3 (`data/combinatorial-genesis/library/parameters.json`)
   - **Замороженный набор данных**: Последняя неизменяемая версия комбинаторного набора данных (`data/combinatorial-genesis/datasets/latest.json`)

2. **Векторное кэширование**: Реализует интеллектуальное кэширование для избежания избыточной генерации эмбеддингов:
   - Переиспользует существующие эмбеддинги из предыдущих запусков
   - Интегрируется с семантическим кэшем Flowmusic
   - Генерирует эмбеддинги только для новых или изменённых параметров

3. **Генерация эмбеддингов**: Использует Ollama для генерации текстовых эмбеддингов:
   - Модель по умолчанию: `qwen3-embedding:4b` (настраивается через `OLLAMA_EMBED_MODEL`)
   - Пакетная обработка с настраиваемым размером пакета (по умолчанию: 64)
   - Нормализует все векторы до единичной длины для косинусного сходства

4. **Сохранение индекса**: Хранит два файла:
   - `embeddings.f32`: Бинарный файл с нормализованными векторами float32 (заголовок: количество, размерность)
   - `manifest.json`: Метаданные, включая информацию о модели, хэш кэша и ссылки на файлы

### Методы

**Классификация области поиска**: Параметры автоматически классифицируются в одну из пяти областей:
- `sound`: Параметры синтеза и обработки звука (по умолчанию)
- `structure`: Аранжировка, секвенирование, тайминг, ритм
- `metadata`: Описательные и классификационные метаданные
- `provenance`: Отслеживание владельца и происхождения
- `administrative`: Контракты и административные элементы управления

**Конструкция текста для эмбеддинга**: Два различных текстовых представления:
- `retrieval_text`: Технические поля для поиска (technical_name, category, sub_category, quantity_kind, semantic_keywords, lyria_prompt_tags)
- `semantic_text`: Естественно-языковое описание для семантического поиска (name_ru, описания, теги, ключевые слова)

### Цели

- **Унифицированный поиск**: Обеспечить единый интерфейс семантического поиска по всем источникам параметров
- **Инкрементальные обновления**: Минимизировать вычислительные затраты за счёт переиспользования существующих эмбеддингов
- **Переносимость моделей**: Поддержка различных моделей эмбеддингов через Ollama
- **Быстрое извлечение**: Бинарный формат для эффективных векторных операций во время выполнения

### Использование

```bash
python python_engine/build-genesis-v3-composite-index.py \
  --model qwen3-embedding:4b \
  --endpoint http://localhost:11434 \
  --batch-size 64
```

Составной индекс автоматически строится как заключительный этап пайплайна Combinatorial Genesis.

## 2. Audio CLAP RAG

### Назначение

Audio CLAP RAG обеспечивает кросс-модальный поиск аудио-в-параметры. Пользователи могут выбрать аудио-фрагмент, и система анализирует его акустические характеристики для поиска семантически похожих аудио-параметров управления с использованием модели LAION-CLAP.

### Архитектура

```
Audio CLAP RAG: Поток кросс-модального поиска
├── Фронтенд (React-компонент)
│   └── searchAudio() нажатие кнопки
│       └── POST /api/audio/search
│
├── API-маршрут Next.js
│   ├── POST-обработчик получает FormData
│   ├── Запись аудио во временный файл
│   └── callSidecar("audio_search")
│       └── Запускает Python-процесс
│
└── Python-бэкенд (audio_clap_rag.py)
    ├── search_audio() точка входа
    │   ├── build_index() обеспечивает индекс
    │   │   ├── Загрузка параметров V3
    │   │   ├── Пакетное кодирование текста через CLAP
    │   │   └── Сохранение index.json
    │   ├── librosa.load() аудио-фрагмент
    │   ├── Разделение на 10-секундные чанки
    │   ├── model.get_audio_features()
    │   ├── np.mean() усреднение чанков
    │   ├── np.dot() косинусное сходство
    │   └── _active_parameter() форматирование
    └── Возврат результатов в API
```

### Принципы работы

1. **Кросс-модальные эмбеддинги**: Модель LAION-CLAP кодирует и аудио, и текст в общее пространство эмбеддингов:
   - Модель: `laion/clap-htsat-fused` (настраивается через `CLAP_MODEL`)
   - Устройство: CPU по умолчанию (настраивается через `CLAP_DEVICE`)
   - Аудио обрабатывается на 48kHz моно

2. **Инкрементальное построение индекса**: Текстовый индекс строится инкрементально:
   - Загружает параметры V3 из библиотеки и замороженного набора данных
   - Вычисляет хэш содержимого для каждого параметра
   - Переиспользует существующие эмбеддинги, если содержимое параметра не изменилось
   - Кодирует только новые или изменённые параметры

3. **Пайплайн обработки аудио**:
   - Загружает выбранный аудио-фрагмент с указанным смещением и длительностью
   - Разделяет длинные фрагменты на 10-секундные чанки
   - Кодирует каждый чанк через модель CLAP
   - Усредняет эмбеддинги чанков в единый вектор запроса
   - Нормализует вектор для косинусного сходства

4. **Поиск по сходству**: Вычисляет косинусное сходство между аудио-вектором и всеми текстовыми векторами параметров:
   - Скалярное произведение нормализованных векторов
   - Ранжирует результаты по оценке сходства
   - Нормализует оценки в диапазон 0-1 для отображения в UI

5. **Генерация активных параметров**: Преобразует лучшие совпадения в активные параметры:
   - Предлагаемые значения на основе нормализованной силы сходства
   - Technical_name, category, unit, диапазон и значение по умолчанию
   - Готово для генерации макроса и экспорта аудио

### Методы

**Разбивка текста на чанки**: Метаданные параметров структурируются в приоритетные поля:
1. technical_name, name_ru, description_en, description_ru
2. category, sub_category, semantic_keywords, lyria_prompt_tags
3. domain, axes, quantity_kind
4. Все остальные поля

**Каноническое хеширование**: SHA-256 хэш канонического JSON-представления для обнаружения изменений:
- Отсортированные ключи, без пробелов
- Используется для определения необходимости перекодирования параметра

**Разбивка аудио на чанки**: Длинные аудио-сегменты обрабатываются в 10-секундных окнах:
- Поддерживает фрагменты от 1 до 800 секунд
- Каждый чанк кодируется независимо
- Итоговый вектор — среднее всех векторов чанков

### Цели

- **Интуитивное открытие**: Находить параметры, описывая звук аудио-примерами
- **Кросс-модальный поиск**: Преодолеть разрыв между акустической интуицией и техническими параметрами
- **Инкрементальные обновления**: Эффективно поддерживать индекс при росте каталога параметров
- **Обратная связь в реальном времени**: Обеспечить интерактивное исследование параметров на основе аудио

### Использование

**Фронтенд** (`/audio-clap-rag`):
1. Загрузить или выбрать аудио-файл
2. Выбрать фрагмент на волне (смещение и длительность)
3. Установить top-K (количество результатов, 3-100)
4. Нажать "Найти параметры"
5. Просмотреть совпавшие параметры и экспортировать макрос

**CLI** (для управления индексом):
```bash
# Построить или обновить текстовый индекс CLAP
python python_engine/audio_clap_rag.py
```

### Зависимости

- `torch`: PyTorch для инференса модели CLAP
- `transformers`: Библиотека Hugging Face transformers
- `librosa`: Загрузка и обработка аудио
- `numpy`: Векторные операции

## 3. Combinatorial Genesis

### Назначение

Combinatorial Genesis — это автоматизированный пайплайн, который обрабатывает новые предложения параметров из файлов Flowmusic inbox через качество-фильтрацию, семантический анализ и замораживание набора данных. Он преобразует необработанные выводы LLM в курируемый, неизменяемый набор данных параметров, готовый для синтеза.

### Архитектура

```
Combinatorial Genesis: Пайплайн
├── Триггер фронтенда
│   └── API-обработчик
│       └── run-combinatorial-pipeline.py
│           ├── acquire_lock()
│           ├── subprocess.run() для каждого этапа
│           │   ├── collect-json-from-folder.py
│           │   ├── prepare-combinatorial-corpus.py
│           │   │   ├── build_quality_gate()
│           │   │   ├── load_or_create_embeddings()
│           │   │   │   └── embed_batch() → Ollama
│           │   │   ├── build_semantic_review()
│           │   │   │   ├── signatures()
│           │   │   │   └── approximate_neighbor_pairs()
│           │   │   ├── build_auto_triage()
│           │   │   └── build_semantic_groups()
│           │   │       └── union-find слияние
│           │   ├── freeze-combinatorial-dataset.py
│           │   │   └── version_dir.mkdir()
│           │   ├── build-combinatorial-runtime-index.py
│           │   │   └── embedder() → Ollama
│           │   └── build-genesis-v3-composite-index.py
│           └── write_report()
```

### Принципы работы

1. **Сбор** (`collect-json-from-folder.py`):
   - Читает файлы Flowmusic inbox (`.txt`, `.md`)
   - Парсит JSON-батчи из LLM-разговоров
   - Извлекает появления параметров с provenance
   - Выполняет дедупликацию по точным именам
   - Нормализует technical_name в английский snake_case где безопасно
   - Разделяет валидные параметры и карантин

2. **Качество-фильтр** (`prepare-combinatorial-corpus.py`):
   - Исключает параметры с повторяющимися токенами
   - Фильтрует параметры с избыточной длиной
   - Удаляет параметры с проблемами качества
   - Строит корпус атомов из допустимых параметров
   - Генерирует отчёт о качестве с объяснениями

3. **Семантические эмбеддинги**:
   - Эмбеддинг-преобразование допустимых параметров через Ollama
   - Кэширование эмбеддингов для инкрементальных обновлений
   - Поддержка пакетной обработки с настраиваемым размером
   - Хранение эмбеддингов в бинарном формате с метаданными

4. **Семантический обзор**:
   - Использует разреженные гиперплоскостные сигнатуры для приближённого поиска ближайших соседей
   - Ранжирует кандидатов по точному косинусному сходству
   - Генерирует очередь обзора для ручной инспекции
   - Вычисляет BGE-оценки для классификации same/related/distinct

5. **Автоматическая триировка**:
   - Автоматически классифицирует пары параметров как:
     - `same`: Семантически эквивалентны (кандидаты на слияние)
     - `related`: Похожи но различны (хранить отдельно)
     - `distinct`: Несвязаны (хранить отдельно)
   - Применяет консервативные пороги для избежания ложных слияний
   - Хранит решения для ручного переопределения

6. **Семантические группы**:
   - Применяет алгоритм union-find для слияния параметров, классифицированных как `same`
   - Создаёт канонические группы с представительским параметром
   - Генерирует семантический черновик с дедуплицированными записями
   - Сохраняет provenance для всех объединённых параметров

7. **Замораживание** (`freeze-combinatorial-dataset.py`):
   - Создаёт набор данных с адресацией по содержимому
   - ID версии: `cg-v1-{content-sha256}`
   - Неизменяемость: то же содержимое производит тот же ID версии
   - Хранит: parameters.json, atoms.json, semantic_groups.json
   - Обновляет указатель `latest.json` на новую версию

8. **Runtime-индекс** (`build-combinatorial-runtime-index.py`):
   - Эмбеддинг-преобразование корпуса атомов из замороженного набора данных
   - Использует Ollama для текстовых эмбеддингов
   - Хранит в бинарном формате для быстрого поиска
   - Обеспечивает генерацию параметров на основе атомов в синтезе

9. **Составной индекс** (`build-genesis-v3-composite-index.py`):
   - Строит финальный составной индекс V3
   - Объединяет библиотеку и замороженный набор данных
   - Обеспечивает унифицированный семантический поиск по всем источникам

### Методы

**Фильтрация качества**:
- Обнаружение повторения токенов
- Пороги длины (technical_name, описания)
- Валидация паттернов (technical_name должен быть snake_case)
- Валидация unit и quantity_kind

**Семантические сигнатуры**:
- Разреженные гиперплоскостные проекции для быстрого приближённого поиска
- Настраиваемое количество гиперплоскостей
- Используются для поиска пар-кандидатов перед точным косинусным сравнением

**Слияние Union-Find**:
- Структура данных непересекающихся множеств для группировки
- Сжатие пути для эффективности
- Объединение по рангу для сбалансированных деревьев
- Группирует параметры, классифицированные как `same`

**Адресация по содержимому**:
- SHA-256 хэш канонического JSON-представления
- ID версии производный от хэша
- Предотвращает дубликаты версий
- Обеспечивает кэширование на основе содержимого

### Цели

- **Автоматическая кураторская обработка**: Преобразовать необработанные выводы LLM в качественный каталог параметров
- **Семантическая дедупликация**: Идентифицировать и объединить семантически эквивалентные параметры
- **Неизменяемая история**: Поддерживать версионированный набор данных с адресацией по содержимому
- **Инкрементальная обработка**: Эффективно обрабатывать новый inbox без полной пересборки
- **Контроль качества**: Многоэтапная фильтрация обеспечивает попадание в каталог только валидных параметров

### Использование

**Фронтенд** (`/combinatorial-genesis`):
1. Поместить новые экспорты Flowmusic в `flowmusic-inbox/`
2. Нажать "Обработать inbox"
3. Мониторить прогресс пайплайна с живыми логами
4. Просмотреть семантические решения и переопределить при необходимости
5. Просмотреть замороженную версию и статус runtime-индекса

**CLI**:
```bash
# Запуск полного пайплайна
python python_engine/run-combinatorial-pipeline.py

# Запуск отдельных этапов
python python_engine/collect-json-from-folder.py flowmusic-inbox/
python python_engine/prepare-combinatorial-corpus.py
python python_engine/freeze-combinatorial-dataset.py
python python_engine/build-combinatorial-runtime-index.py
python python_engine/build-genesis-v3-composite-index.py
```

### Выходные файлы

**Этап сбора** (`flowmusic-output/`):
- `flowmusic_batches.json`: Необработанные батчи с ошибками и provenance
- `flowmusic_occurrences.json`: Валидные появления
- `flowmusic_rejected_occurrences.json`: Карантин с ошибками валидации
- `unified_parameters_lexical.json`: Канонические записи по точным именам
- `collection_report.json`: Статистика и метрики

**Этап корпуса**:
- `eligible_parameters.json`: Параметры после фильтрации качества
- `quality_report.json`: Объяснения для параметров в карантине
- `atom_corpus.json`: Английские атомы с частотами
- `semantic_review_queue.json`: Пары с BGE-оценками для обзора
- `semantic_auto_triage.json`: Автоматические решения same/related/distinct
- `semantic_groups.json`: Объединённые семантические группы
- `unified_parameters_semantic_draft.json`: Семантически дедуплицированный черновик
- `semantic_embeddings.f32`: Кэшированные эмбеддинги

**Замороженный набор данных** (`datasets/cg-v1-{hash}/`):
- `parameters.json`: Финальные записи параметров
- `atoms.json`: Корпус атомов
- `semantic_groups.json`: Назначения семантических групп
- `manifest.json`: Метаданные версии и SHA-256

**Runtime-индекс** (`indexes/{version-id}/`):
- Бинарные эмбеддинги атомов для быстрого поиска

## 4. Combinatorial Synthesis

### Назначение

Combinatorial Synthesis — это ориентированный на пользователя рабочий процесс генерации параметров. Пользователи предоставляют структурные источники (существующие параметры для рекомбинации) и семантические цели (желаемые характеристики), и система генерирует новые кандидаты параметров через рекомбинацию атомов и ранжирование BGE.

### Архитектура

```
Combinatorial Synthesis: Поток генерации параметров
├── Пользовательский интерфейс (CombinatorialSynthesisPage)
│   └── generate() нажатие кнопки
│
├── API-маршрут (preview/route.ts)
│   ├── embedText(query)
│   ├── rankRuntimeAtoms(queryEmbedding)
│   │   └── runtime-index.ts
│   │       └── вычисление косинусного сходства
│   ├── CombinatorialGenerator.generate()
│   │   └── core.ts
│   │       └── объединение токенов → technical_name
│   ├── embedTexts(candidates)
│   ├── сортировка по normalizedCosine()
│   └── inferCandidateValues()
│
└── Опциональное улучшение LLM
    └── normalize-metadata API-вызов
```

### Принципы работы

1. **Эмбеддинг семантического запроса**:
   - Пользователь предоставляет естественно-языковое описание желаемых параметров
   - Запрос эмбеддинг-преобразуется через модель эмбеддингов Ollama
   - Используется для ранжирования атомов и кандидатов

2. **Ранжирование атомов**:
   - Ищет в замороженном индексе атомов атомы, похожие на семантический запрос
   - Вычисляет косинусное сходство между запросом и всеми эмбеддингами атомов
   - Возвращает top-K атомов (по умолчанию: 180) для генерации кандидатов

3. **Генерация кандидатов**:
   - Объединяет атомы с использованием детерминированных шаблонов
   - Шаблоны паттернов: структуры descriptor-concept-property
   - Генерация на основе сида для воспроизводимости
   - Ограничение количества кандидатов (по умолчанию: 300, настраивается)
   - Принудительный точный стоп-лист (библиотека + замороженный набор данных)

4. **Переранжирование BGE**:
   - Пакетное эмбеддинг-преобразование всех сгенерированных technical_names
   - Сортировка кандидатов по косинусному сходству к семантическому запросу
   - Фильтрация до запрошенного лимита (по умолчанию: 30)
   - Сохранение структурного разнообразия в топ-результатах

5. **Вывод значений**:
   - Экстраполяция UI-элемента, unit, min/max/step/default из семантически похожих параметров-доноров
   - Доноры ранжируются по BGE-сходству к полному имени кандидата
   - Требует консенсуса среди нескольких доноров для авто-разрешения
   - Конфликтующие доноры помечают кандидата как `needs_review`

6. **Нормализация LLM** (опционально):
   - Отправляет кандидатов в чат-модель для генерации описаний
   - Модель читает неизменяемую схему управления, теги, ключевые слова и метаданные доноров
   - Возвращает: name_ru, description_en, description_ru и рекомендацию отбора
   - Кандидаты обрабатываются по одному для удержания модели в памяти
   - Поддерживает отмену и повтор при ошибке

7. **Управление пакетами**:
   - Сохранение черновика: пакет с адресацией по содержимому в `drafts/`
   - Dry-run: симуляция публикации и проверка коллизий
   - Публикация: добавление в автономную библиотеку с резервной копией в `library/history/`
   - Идемпотентность: тот же ID пакета публикуется только один раз

### Методы

**Выбор атомов**:
- Атомы ранжируются по семантическому сходству к запросу
- Фильтрация по ролям (descriptor, concept, property)
- Взвешивание по частоте из корпуса атомов

**Генерация по шаблонам**:
- Детерминированный сид для воспроизводимости
- Паттерн-объединение: descriptor + concept + property
- Принудительный стоп-лист по точным именам
- Обнаружение коллизий с существующими параметрами

**Правила вывода значений**:
- Вывод только из совместимых доноров (тот же quantity_kind, ui_element)
- Доноры должны соглашаться по unit, диапазону и options
- Оценка уверенности на основе консенсуса доноров
- `needs_review` если доноры не согласны или недостаточно данных

**Нормализация LLM**:
- Использует чат-модель из общих настроек
- Читает метаданные доноров для контекста
- Валидирует вывод по схеме
- Обрезает чрезмерно длинный текст на границе предложения/слова
- Повтор при ошибках JSON или валидации

### Цели

- **Генерация пользователем**: Позволить пользователям генерировать параметры на основе их целей
- **Семантическое выравнивание**: Согласовать сгенерированные параметры с намерением пользователя
- **Структурная согласованность**: Обеспечить соответствие сгенерированных имён соглашениям об именовании
- **Надёжность значений**: Выводить значения управления из похожих существующих параметров
- **Контроль качества**: Ручной обзор перед публикацией в библиотеку

### Использование

**Фронтенд** (`/combinatorial-synthesis`):
1. Ввести семантический запрос (например, "bass filter with resonance")
2. Выбрать исходные параметры (macro) или оставить пустым для полного поиска атомов
3. Установить параметры генерации (seed, limit, source_count)

8. Опционально: "Normalize descriptions" с LLM
9. Сохранить пакет

11. Опубликовать в автономную библиотеку

### Выход

**Ответ превью**:
- Ранжированные кандидаты с technical_name
- Родительские параметры (структурные источники)
- Оценка сходства запроса

## 5. Meta-Crystal V3 Lab

### Назначение

Meta-Crystal V3 Lab — это система предложений параметров с assists LLM. Она использует RAG для извлечения релевантных конфигураций Meta-Crystal и существующих параметров V3, затем инструктирует локальный LLM генерировать новые предложения параметров, следуя протоколу сбора Flowmusic. Все предложения требуют ручного обзора перед публикацией.

### Архитектура

```
Meta-Crystal V3 Lab: Поток
├── Пользовательский интерфейс (MetaCrystalV3LabPage)
│   └── propose() кнопка
│       └── POST /api/meta-crystal-v3-lab/propose
│
├── API-маршрут (propose/route.ts)
│   ├── buildRAGContext(query)
│   ├── embedText(query)
│   ├── rankCompositeNames(queryEmbedding)
│   ├── загрузка настроек эмбеддинга
│   ├── загрузка протокола сбора
│   ├── чат с LLM (JSON-схема)
│   ├── validateLabParameters()
│   ├── опциональный повтор при ошибке валидации
│   └── возврат кандидатов с контекстом
│
├── Маршрут валидации (validate/route.ts)
│   ├── validateLabParameters()
│   └── возврат ошибок/предупреждений
│
└── Маршрут рейтинга (rating/route.ts)
    └── логирование обратной связи up/down
```

### Принципы работы

1. **Построение RAG-контекста**:
   - Ищет в базе данных Meta-Crystal релевантные конфигурации
   - Извлекает имена кристаллов, оценки и фрагменты
   - Предоставляет LLM доказательства из существующих дизайнов кристаллов

2. **Контекст коллизий V3**:
   - Эмбеддинг-преобразование запроса пользователя через Ollama
   - Поиск в составном индексе V3 ближайших параметров
   - Возврат top-K ближайших соседей (по умолчанию: 18)
   - Скрытие точных имён параметров от LLM для предотвращения имитации
   - Сервер выполняет проверку коллизий после генерации

3. **Протокол сбора**:
   - LLM инструктирован следовать протоколу сбора Flowmusic
   - Протокол загружен из `docs/prompts/FLOWMUSIC_COLLECTION_PROMPT_V1.md`
   - Принудительная JSON-схема со всеми обязательными полями
   - Указание переопределения размера батча (запрошенное количество против фиксированных 10)

4. **Принудительная JSON-схема**:
   - Строгая схема с regex-паттернами для technical_name, quantity_kind
   - Варианты UI-элементов: Range, Select, Toggle, Text, String, Array
   - Обязательные поля: technical_name, name_ru, описания, category, unit, теги, ключевые слова
   - Валидация русских ключевых слов на наличие кириллицы
   - Валидация английских ключевых слов только на ASCII

5. **Пайплайн валидации**:
   - Проверка коллизий technical_name с существующими параметрами V3
   - Валидация соответствия JSON-схеме
   - Проверка наличия обязательных полей
   - Валидация regex-паттернов
   - Возврат ошибок и предупреждений для ручной коррекции

6. **Автоматический повтор**:
   - При ошибке валидации отправляет коррекцию в LLM
   - LLM инструктирован исправить конкретные ошибки без изменения валидных полей
   - Сохраняет первую попытку если повтор также неудачен
   - Раскрывает обе необработанные попытки для отладки

7. **Ручной обзор**:
   - JSON можно редактировать вручную в UI
   - "Check schema" повторно валидирует после редактирования
   - Кандидаты должны быть одобрены индивидуально
   - Только кандидаты без ошибок могут быть упакованы

8. **Пакет и публикация**:
   - Одобренные кандидаты сохраняются как пакет
   - Dry-run проверяет коллизии и ошибки схемы
   - Публикация добавляет в автономную библиотеку
   - Требует Managed Rebuild V3 для участия в поиске

9. **Обратная связь по рейтингу**:
   - Пользователи могут оценивать кандидатов как up/down
   - Рейтинги логируются в `data/combinatorial-genesis/meta-crystal-v3-lab/ratings.jsonl`
   - Используются для будущего улучшения качества предложений

### Методы

**Извлечение RAG**:
- Использует существующий пайплайн RAG из `/api/llm/chat`
- Ищет описания и конфигурации кристаллов
- Возвращает контекст с kind, name, score и snippet

**Поиск по составному индексу**:
- Использует составной индекс V3 для поиска ближайших соседей
- Косинусное сходство между запросом и эмбеддингами параметров
- Возвращает имена параметров и оценки сходства
- Скрыто от LLM для предотвращения имитации имён

**Валидация схемы**:
- Regex-паттерн: `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$` для technical_name
- Regex-паттерн: `^[A-Za-z0-9][A-Za-z0-9 _/().,+%'-]*$` для тегов и ключевых слов
- Валидация длины массивов (3 тега, 3+4 ключевых слова)
- Валидация полей специфичных для UI-элемента (min/max/step для Range, options для Select)

**Обнаружение коллизий**:
- Проверка technical_name против всех параметров V3
- Предотвращение дубликатов имён
- Требует от LLM генерации действительно разных имён при повторе

### Цели

- **Использование существующих знаний**: Использовать дизайны Meta-Crystal как вдохновение для новых параметров
- **Семантическое выравнивание**: Генерировать параметры, соответствующие цели кураторства пользователя
- **Предотвращение имитации**: Скрывать существующие имена V3 для поощрения оригинальности
- **Обеспечение качества**: Многоэтапная валидация обеспечивает высококачественные предложения
- **Человек в контуре**: Ручной обзор и редактирование перед публикацией
- **Обратная связь**: Система рейтинга для непрерывного улучшения

### Использование

## Интеграция между режимами

Пять режимов приложения работают вместе в жизненном цикле параметров:

1. **Meta-Crystal V3 Lab**: Предлагает новые параметры на основе дизайнов Meta-Crystal
2. **Combinatorial Synthesis**: Генерирует параметры через рекомбинацию атомов
3. **Combinatorial Genesis**: Обрабатывает необработанные предложения в замороженный набор данных
4. **Flowmusic Genesis V3**: Строит составной индекс из библиотеки + замороженного набора данных
5. **Audio CLAP RAG**: Обеспечивает аудио-открытие всех параметров

### Поток данных

```
Meta-Crystal V3 Lab → предложения → Combinatorial Genesis → замороженный набор данных
                                                            ↓
Combinatorial Synthesis → кандидаты → Combinatorial Genesis → замороженный набор данных
                                                            ↓
                                              Flowmusic Genesis V3 → составной индекс
                                                            ↓
                                              Audio CLAP RAG → аудио-поиск
```

### Общие компоненты

- **Ollama**: Общий бэкенд моделей эмбеддингов и чата
- **Автономная библиотека**: Библиотека параметров V3, используемая всеми режимами
- **Составной индекс**: Унифицированный поисковый индекс для параметров V3
- **Система пакетов**: Управление пакетами с адресацией по содержимому для синтеза и лаборатории

## Конфигурация

### Настройки Ollama

Все режимы используют общую конфигурацию Ollama из `/api/settings`:

- **Модель эмбеддингов**: По умолчанию `qwen3-embedding:4b` (настраивается)
- **Чат-модель**: По умолчанию `hermes3:3b` или `qwen2.5-3b` (настраивается)
- **Endpoint**: По умолчанию `http://localhost:11434` (настраивается)
- **Temperature**: По умолчанию 0.7 (снижается до 0.1 для структурированной генерации)
- **Max Tokens**: По умолчанию 4096

### Переменные окружения

- `OLLAMA_BASE_URL`: API-endpoint Ollama
- `OLLAMA_EMBED_MODEL`: Модель эмбеддингов по умолчанию
- `CLAP_MODEL`: Имя модели LAION-CLAP (по умолчанию: `laion/clap-htsat-fused`)
- `CLAP_DEVICE`: Устройство CLAP (по умолчанию: `cpu`)

### Совместимость моделей

При изменении модели Ollama необходимо перестроить:
- Runtime-индекс атомов (Combinatorial Synthesis)
- Составной индекс V3 (Flowmusic Genesis V3)
- Текстовый индекс CLAP (Audio CLAP RAG - если модель изменена)

Векторы от разных моделей несовместимы.

## Устранение неполадок

### Индекс не готов

**Симптом**: Поиск возвращает ошибку "index not built"

**Решение**:
- Запустить соответствующую команду построения индекса для режима
- Для Audio CLAP RAG: Нажать "Update CLAP index" в UI
- Для Combinatorial Synthesis: Убедиться, что runtime-индекс построен через пайплайн
- Для Flowmusic Genesis V3: Запустить пайплайн или автономный скрипт

### Модель изменена, но индекс не перестроен

**Симптом**: Поиск возвращает результаты низкого качества или ошибки

**Решение**:
- Перестроить все индексы после изменения модели Ollama
- Удалить старые файлы индекса для принудительной пересборки
- Проверить, что модель в манифесте индекса соответствует текущим настройкам

### Параметр не найден в поиске

**Симптом**: Newly published parameter doesn't appear in search results

**Решение**:
- Запустить Managed Rebuild V3 для составного индекса
- Перестроить текстовый индекс CLAP для аудио-поиска
- Проверить, что параметр находится в library/parameters.json

### Ошибка генерации LLM

**Симптом**: Lab или synthesis возвращает ошибки валидации

**Решение**:
- Просмотреть необработанный ответ LLM в UI (раскрываемая секция)
- Редактировать JSON вручную для исправления ошибок
- Попробовать более низкую temperature для более детерминированного вывода
- Проверить, что чат-модель загружена в Ollama

### Аудио-поиск не возвращает результатов

**Симптом**: Audio CLAP RAG возвращает пустые результаты

**Решение**:
- Проверить, что CLAP-индекс построен
- Проверить, что аудио-фрагмент валиден (не пуст, правильный формат)
- Попробовать большую длительность (минимум 1 секунда)
- Увеличить top-K для просмотра большего количества результатов

## Соображения производительности

### Генерация эмбеддингов

- **Размер пакета**: Большие пакеты уменьшают накладные расходы API но используют больше памяти
- **Кэширование**: Все режимы реализуют инкрементальное кэширование для избежания избыточных эмбеддингов
- **Параллелизм**: Локальный Ollama обычно настроен на `OLLAMA_NUM_PARALLEL=1`

### Размер индекса

- **Составной индекс**: Растёт с количеством параметров (библиотека + замороженный набор данных)
- **Runtime-индекс**: Зависит от размера корпуса атомов (обычно меньше полного набора данных)
- **CLAP-индекс**: Один вектор на параметр с текстовыми метаданными

### Производительность поиска

- **Косинусное сходство**: O(n) для наивного поиска, приемлемо для текущего размера каталога
- **Бинарный формат**: Векторы хранятся как float32 для эффективной загрузки
- **Инкрементальные обновления**: Только новые/изменённые параметры требуют перекодирования

## Будущие улучшения

Потенциальные улучшения режимов приложения:

1. **Индекс HNSW**: Заменить наивный косинусный поиск на HNSW для более быстрого извлечения
2. **Поддержка нескольких моделей**: Разрешить разные модели для разных режимов
3. **Параллельное эмбеддинг-преобразование**: Увеличить параллелизм Ollama для более быстрой сборки индекса
4. **GPU CLAP**: Использовать GPU для инференса модели CLAP (в настоящее время только CPU)
5. **Семантический diff**: Показывать изменения параметров между замороженными версиями
6. **Авто-публикация**: Опциональная авто-публикация для высокоуверенных кандидатов
7. **Кросс-режимный поиск**: Унифицированный поиск по всем источникам параметров
8. **Связи параметров**: Отслеживать и визуализировать зависимости параметров
